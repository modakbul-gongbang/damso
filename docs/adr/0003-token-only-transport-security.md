# ADR 0003: Trade app-level TLS for a bearer token on a trusted private network

## Status

Accepted (2026-08). Supersedes the transport-security half of [ADR 0002](0002-http-client-server.md): the self-signed certificate, the trust-on-first-use fingerprint pin, and the Keychain-stored token are removed. Everything else ADR 0002 decided - the HTTP daemon as the sole store owner, the `/v1` and `/mcp` surface, the processing queue, the clean-cut migration style - stands unchanged.

## Context

ADR 0002 made Damso's own daemon responsible for authentication and encryption once it replaced SSH: a self-signed certificate generated by `make install-server`, its fingerprint pinned by the client at pairing time, and a bearer token on every request. It named that new security surface "the dominant risk this change accepts."

Ten months of single-owner use produced one concrete piece of evidence against the certificate half of that decision, and one about where the privacy actually comes from:

- **The certificate blocked the very clients the `/mcp` endpoint exists for.** The generated certificate carries exactly one SAN, `DNS:damso-server`, because at generation time the server does not know the hostname the operator will eventually dial. The Swift app never noticed - it pins fingerprint bytes and skips hostname validation entirely - but every standard MCP client does the ordinary thing and validates the hostname, so it fails with `ERR_TLS_CERT_ALTNAME_INVALID` against the real address. Connecting Claude Code to a remote store required a `/etc/hosts` alias mapping the SAN name to the server's address plus a `NODE_EXTRA_CA_CERTS` injection of the certificate. That is not a configuration a second user would discover, and "any MCP client points at one URL" was one of ADR 0002's motivating goals.
- **The transport was already private.** The real deployment reaches the server Mac over Tailscale, so WireGuard already provides encryption and device authentication below Damso. The app's own TLS was a second, weaker layer (no CA, no hostname binding, one long-lived key) wrapped around a channel that was already encrypted.

The token half of ADR 0002 held up on its own terms and is not in question here: the server Mac is shared with other users' background agents and the store holds meeting audio, transcripts, and people profiles, so an unauthenticated daemon on the tailnet would expose all of it to any device on that network.

## Decision

The bearer token is the only credential, and the transport is plain HTTP in both modes.

- **No certificate anywhere.** `damso.server.credentials` generates and loads a token and nothing else; the server never configures a TLS listener, whatever host it binds. `TLSPinning.swift` and its trust-on-first-use counterpart are deleted, and pairing no longer has a fingerprint step to confirm.
- **The token moves from the Keychain to a 0600 file** under `~/Library/Application Support/Damso/.client-credentials/`, mirroring how the server has always stored the same secret. It is anchored to the fixed application-support directory rather than the user-selectable storage root, so it never rides along with a store export or relocation - the client-side half of D-24's rule. The Keychain wrapper (`SecretStore`) is removed outright; its only other account was a Plaud session that no production code ever read.
- **Transport privacy becomes an explicit product premise, stated rather than enforced.** README and INSTALL say remote mode belongs on a Tailscale tailnet, a VPN, or a trusted LAN, and the pairing pane warns when the entered address is not private - RFC1918, the `100.64/10` CGNAT range Tailscale uses, a `*.ts.net` name, or loopback all count as private. The warning never blocks: an operator can have a legitimate reason for an address that does not pattern-match, and a hard block would be a worse failure than a dismissible warning.
- **Upgrading is a re-pair, not a migration.** A client still holding an HTTPS-era pairing is detected by its stored fingerprint preference and shown a re-pair notice instead of silently failing; the operator re-runs `make install-server` for a fresh token and pairs again. The store's file format is unchanged, so no data moves. This is the same clean-cut shape ADR 0002 used to retire SSH.

### Amendment: only two paths answer without a token

Removing the certificate makes the token the *entire* remote boundary, which raised the value of auditing what that boundary lets through. `UNAUTHENTICATED_PATHS` carried four entries inherited from ADR 0002: `/v1/health`, `/v1/version`, `/openapi.json`, and `/docs`. Only the first two are justified - a client probing "is a server here, and what does it speak" during pairing genuinely has no token yet. The other two were FastAPI's defaults never revisited: no client flow requests them, and MCP Streamable HTTP does not read a schema document, but the exemption handed the full route list to anything that could reach the port. They are token-gated now. Local mode is unaffected because the middleware short-circuits before the exemption check, so the schema is still browsable on the machine that owns the store.

This narrows a contract the PRD recorded as preserved (R2 named all four paths). The narrowing was found by a post-delivery audit and decided by the operator afterward, so it is recorded here rather than backdated into a finalized PRD.

## Consequences

- **An MCP client is now a URL and a header.** `http://<server-host>:<port>/mcp` with `Authorization: Bearer <token>` works in any Streamable-HTTP client with no certificate trust, no host alias, and no environment variable - the outcome ADR 0002 wanted and its own certificate prevented.
- **Damso no longer provides confidentiality on the wire; the operator's network does.** Anyone who can observe traffic between the two Macs can read meeting content and capture the token. This is acceptable only under the premise above, and it is the reason that premise is documented and warned about rather than left implicit. The moment a server is reachable from a network the operator does not trust, this decision is wrong and must be revisited - most likely by putting a real reverse proxy with a CA-issued certificate in front of the daemon rather than by reviving self-signed pinning.
- **The token's blast radius is unchanged and still coarse.** One token per server, shared by the app and every MCP client, so a leak means `make regenerate-server-credentials` and re-pairing everything. Regeneration still takes effect on the running process's next request, with no grace period. Per-client tokens were considered and rejected: an issue-and-revoke table is a management surface this scale does not justify.
- **Rate limiting stays deferred, now with the token as the sole barrier.** The token is 32 bytes of `secrets.token_urlsafe` entropy, so online brute force is not a real threat, and the reachable population is bounded by the same private-network premise. Revisit together with the exposure condition above, not separately.
- **ATS still needs `NSAllowsArbitraryLoads`,** for the opposite reason it did before: not to let a pinned self-signed certificate through, but because the connection is now cleartext. A narrower per-domain exception remains impossible, since the server's hostname is chosen at pairing time rather than at build time.

## Alternatives considered

- **Fix the certificate's SAN and keep everything else.** The smallest possible change, and it was the recommended option going into the decision - it would have removed the `/etc/hosts` and `NODE_EXTRA_CA_CERTS` friction on its own. Rejected because it keeps a whole certificate lifecycle (generation, pinning, mismatch handling, re-pair-on-change) whose only remaining job is to re-encrypt a channel Tailscale already encrypts, and because a SAN list still has to guess every name and address an operator might dial.
- **Terminate TLS with `tailscale serve` and a real Let's Encrypt certificate.** Genuinely better security than self-signed pinning and standard-client friendly. Rejected because it makes Tailscale a hard dependency of a product that should also work on a plain trusted LAN, and it moves a security-critical piece of the setup outside anything Damso can verify or explain in its own install steps.
- **Keep both, with app-level TLS as an option.** Rejected for the same reason ADR 0002 rejected a hybrid SSH/HTTP transport: two transport modes mean two connection-health models, two failure shapes, and two things to test, against a simplification that was the entire point of the change.
- **Drop the token too and rely on the network alone.** Rejected outright. The server Mac is shared, the store is the most sensitive data this product touches, and "anyone on the tailnet can read every meeting" is not a boundary the network premise justifies.
